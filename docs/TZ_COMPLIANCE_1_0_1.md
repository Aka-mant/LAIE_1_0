# Аудит соответствия LAIE 1.0.1

**Базовая ветка:** `feat/local-autonomous-hardening`  
**Базовый commit:** `6c6cbd7a14bf28c6605db82333171b4b579e074f`  
**Рабочая ветка аудита:** `audit/tz-1-0-1-compliance`  
**Основание:** утверждённое ТЗ `LAIE_1_0_Local_Autonomous_GPU_TZ`, версия 1.0.1 от 27.11.2026.

Документ фиксирует результаты проверки дерева и просмотренных исходников на момент аудита. Наличие файла или класса само по себе не считается доказательством выполнения функционального требования.

## 1. Краткое заключение

Проект уже содержит существенную основу локальной вычислительной подсистемы: ComputeEngine, отдельные CPU/CUDA-бенчмарки, сквозной benchmark с переносом RAM/VRAM, пакет `services/compute/scheduler`, реестр типов задач, анализ оборудования и оценки памяти.

Однако LAIE пока нельзя признать соответствующей ТЗ целиком. Основные причины:

- доменная структура и интерфейс реализованы только частично;
- не подтверждена сквозная интеграция GPU с реальными доменными алгоритмами;
- не подтверждены на целевой машине миграции и работа PostgreSQL;
- не подтверждена полная сетевая изоляция runtime;
- не подтверждены критерии научной валидации, контроль бюджета и аудит на уровне всей системы;
- покрытие 98% и Ruff не подтверждены отчётами.

Текущий локальный прогон, предоставленный пользователем: **557 passed**, `manage.py check` — без ошибок. Проверка миграций сообщила `No changes detected`, но одновременно выдала timeout при подключении к PostgreSQL. Следовательно, миграционная история реальной БД этим прогоном не проверена.

## 2. Матрица соответствия

Статусы:
- **Частично** — часть механизма присутствует, но весь критерий приёмки не доказан.
- **Не подтверждено** — данных недостаточно для положительного или отрицательного заключения.
- **Не реализовано в проверенном дереве** — необходимые модули/страницы отсутствуют в просмотренном дереве.

## 3. Фактически найденные вычислительные компоненты

В дереве присутствуют:

- `services/compute/engine.py` — базовый CPU/CUDA selector и матричная операция с CPU fallback;
- `services/compute/benchmark.py` — CPU/CUDA benchmark матричного умножения, прогрев и синхронизация CUDA, сравнение точности с float64;
- `services/compute/end_to_end_benchmark.py` — сквозное измерение с переносом CPU RAM → GPU VRAM → CPU RAM;
- `services/compute/scheduler/adaptive_matrix_service.py`;
- `decision_engine.py`, `execution_engine.py`, `execution_types.py`;
- `hardware_monitor.py`, `matrix_memory_guard.py`, `memory_estimator.py`;
- `performance_model.py`, `matrix_performance_trainer.py`;
- `pytorch_adapter.py`, `task_analyzer.py`, `task_registry.py`, `task_types.py`;
- тесты для benchmark, end-to-end benchmark, engine и компонентов scheduler;
- management commands для запуска двух видов benchmark.

Это хорошая основа. Следующий аудит должен проверить не количество модулей, а корректность взаимодействия, безопасность параллельного исполнения, поведение при OOM и реальное использование этих сервисов доменными алгоритмами.

## 4. Подтверждённые проблемы и пробелы

### 4.1 Исправлено в текущей ветке

- `docs/POWERSHELL_SETUP.md` теперь указывает Python 3.14.x и целевую версию 3.14.3 вместо Python 3.13.
- Команда создания виртуального окружения использует `py -3.14`.
- Добавлена явная проверка `python --version`.

### 4.2 Требуют реализации или доказательства

1. Полный runtime network audit: исходящие соединения, URL, HTTP-клиенты, socket, subprocess, telemetry/update checks и зависимости.
2. Проверка реального bind веб-сервера и PostgreSQL listener только на loopback.
3. Подключение PostgreSQL, создание роли/БД, применение всех миграций и integration tests.
4. Глубокий аудит ComputeEngine/scheduler: task queue concurrency, VRAM reserve, batch reduction, bounded retries, fallback, task cancellation, resource limits и журналирование.
5. Интеграция GPU с конкретными вычислительными pipeline LAIE с проверкой численной эквивалентности CPU/GPU.
6. Полная предметная модель тиражей, источников, версий правил, наборов данных, критериев, гипотез, экспериментов, прогнозов, портфелей и аудита.
7. Научные acceptance tests: временное разделение, leakage prevention, baseline, holdout, FDR и корректные интервалы неопределённости.
8. Русскоязычный dashboard и Compute Dashboard.
9. Отчёт coverage с branch coverage и обоснованием исключений, целевое покрытие не менее 98%; Ruff.
10. Проверка запрета автоматической покупки и enforcement лимита 5 000 RUB.

## 5. Рекомендуемая последовательность внедрения

Этапы выполняются последовательно. Каждый этап — отдельная Git-ветка, собственные тесты и отчёт. Следующий этап начинается после проверки результата предыдущего. Merge запрещён до успешного прохождения предусмотренных тестов и явного подтверждения архитектора.

### Этап 0. Baseline и инвентаризация
- Зафиксировать commit, ветку, Python, зависимости, тесты, coverage и Ruff.
- Получить полный список tracked files.
- Провести поиск всех сетевых вызовов, URL, облачных терминов, worker/job инфраструктуры.
- Проверить конфигурацию Django, ASGI/WSGI, management commands и startup scripts.
- Не удалять найденный код до анализа импортов, маршрутов и тестов.

### Этап 1. Локальная среда и БД
- Проверить PostgreSQL server version и listener addresses.
- Подтвердить только loopback bind.
- Создать отдельную роль и базу LAIE с минимальными правами.
- Применить миграции на локальной PostgreSQL.
- Проверить backup/restore и корректное поведение при недоступной БД.
- Проверить запуск Django только на 127.0.0.1.

### Этап 2. ComputeEngine и безопасность исполнения
- Провести API/contract audit engine, adapter и scheduler.
- Установить единые модели Task, Device, ExecutionResult и FailureReason.
- Проверить оценку VRAM и резерв памяти, ограниченную очередь и single-GPU concurrency.
- Реализовать/проверить adaptive batch с ограниченным числом повторов.
- Проверить fallback при CUDA unavailable, OOM и runtime error.
- Фиксировать backend, причину выбора и причину fallback для каждой задачи.

### Этап 3. Бенчмарки и автоматический выбор
- Проверить CPU/GPU benchmark и сквозной benchmark.
- Измерять transfer + compute + output transfer.
- Хранить результаты с версиями Python, PyTorch, CUDA, драйвера и GPU.
- Исключить benchmark, не укладывающийся в память или временные ограничения.
- Выбирать backend по измеренной производительности конкретного класса задач.

### Этап 4. Доменная интеграция GPU
- Выбрать реальные workloads: Monte Carlo, массивные статистические симуляции, обучение поддерживаемых моделей.
- Для каждого workload определить точность и допустимую погрешность.
- Реализовать CPU reference и CUDA adapter.
- Проверить воспроизводимость и численную эквивалентность.
- Не переводить на GPU алгоритмы, где точная арифметика или перенос данных делает это невыгодным.

### Этап 5. Предметные данные и научная достоверность
- Проверить версии правил и призовых таблиц.
- Завершить импорт и provenance данных.
- Внедрить baseline, walk-forward, holdout, leakage checks, FDR и статистические тесты.
- Зафиксировать прогнозы и эксперименты без заднего редактирования.
- Проверить бюджет и запрет автоматической покупки.

### Этап 6. Локальное обучение и планирование
- Реализовать bounded job lifecycle, checkpoint, pause/resume.
- Установить CPU/RAM/VRAM/time/concurrency limits.
- Обеспечить восстановление после перезапуска и защиту от дублирования.
- Не блокировать web-процесс длительными вычислениями.

### Этап 7. UI, аудит и эксплуатация
- Реализовать русскоязычные страницы по разделам ТЗ.
- Создать Compute Dashboard с текущей задачей, backend, VRAM, CPU/RAM, очередью, benchmark history и ошибками.
- Добавить журнал критичных действий и диагностику.
- Проверить доступность только с localhost.

### Этап 8. Приёмка
- Полный pytest и integration suite на PostgreSQL.
- CUDA acceptance suite на RTX 3070; CPU fallback независимо от GPU.
- Fault injection для OOM, CUDA failure и недоступности PostgreSQL.
- Network isolation audit.
- Ruff.
- Coverage >=98% с branch report.
- Performance comparison для реальных workload.
- Итоговый отчёт с доказательствами, ограничениями и списком незакрытых требований.

## 6. Ограничения текущего аудита

- GitHub code search не вернул надёжной полноты результатов; пустой поисковый ответ не трактуется как доказательство отсутствия вызова/зависимости.
- Исходники scheduler представлены множеством модулей; полный построчный аудит каждого из них ещё не выполнен.
- GitHub-проверка не может подтвердить локальную PostgreSQL, CUDA, сетевые сокеты или запуск на Windows компьютере пользователя.
- Текущие 557 тестов и успешный Django check — пользовательский локальный результат, но не полный acceptance по ТЗ.

## 7. Критерий готовности LAIE 1.0.1

Проект считается соответствующим ТЗ только после закрытия всех обязательных пунктов раздела 14 и подтверждения ключевых архитектурных инвариантов на целевой Windows-машине. Наличие тестов без проверки реальных PostgreSQL/CUDA runtime недостаточно. Пустые приложения и документация не заменяют работающие функции.

**Решение аудита:** продолжить поэтапную реализацию. На текущем этапе нельзя объявлять LAIE полностью автономной, полностью GPU-интегрированной или готовой к эксплуатации.
